# RPM Club: спецификация доработки админки

Дата: 22 сентября 2026. Основание: проверка 17 разделов работающей админки, desktop 1440 px и mobile 390 px; `artifacts/admin-ux-2026-09-22/REPORT.md`.

## 1. Цель и согласованные решения

Сотрудник должен находить нужное действие без объяснений разработчика, понимать последствия публикации и не терять введённые данные случайным закрытием формы. Заказчик самостоятельно задаёт награды за приглашения.

Согласовано заказчиком:

- Старые аренды не изменять и не пересчитывать. Не выполнять массовых обновлений аренд, начислений и их финансовых снимков.
- Название и условия награды задаются отдельно для пригласившего и приглашённого.
- Право на награду возникает после первой завершённой оплаченной аренды приглашённого. Выдачу отмечает менеджер; автоматическую скидку эта функция не создаёт.
- Проверка и реализация ведутся локально. Выкладка, изменение действующей программы и отправка сообщений клиентам не входят в локальную проверку.

## 2. Навигация — UX-01

Сохранить существующие адреса и серверные права. Разделить меню на группы «Работа с клиентами», «Контент клуба», «Программа», «Управление». Названия: «Предложения» вместо RPM Drops; «Приглашения друзей» вместо «Рефералы»; «Доставка сообщений» вместо «Доставка»; «База знаний» вместо «Wiki и условия». Bonus остаётся доступен для существующих операций, до отдельного решения о завершении старой механики.

На узком экране заменить боковую колонку из одних иконок кнопкой «Меню». Открытое меню показывает названия, текущую страницу и доступные пользователю разделы. Закрытие: выбор ссылки, Escape, кнопка закрытия. Фокус возвращается на кнопку открытия; фон недоступен для клавиатуры. Добавление сотрудника доступно в разделе «Сотрудники»; глобальную кнопку скрывать на телефоне.

Приёмка: при 390/717/1440 px нет горизонтальной прокрутки самой страницы из-за навигации; все доступные разделы достижимы с клавиатуры; скрытые по роли ссылки не появляются в мобильном меню.

## 3. Настройки и уровни — UX-02

Поле привилегий занимает полную ширину карточки уровня. На телефоне поля располагаются в один столбец. Поля названия, цвета, порога и процента остаются подписаны; единицы ₽ и % явно указаны.

Публикация редакции: 1) изменить условия; 2) проверить влияние порогов; 3) указать причину и подтвердить публикацию. Кнопка публикации недоступна до проверки, рядом объяснено почему. Изменение порога или состава уровней сбрасывает расчёт. Ввод причины и подтверждение не сбрасывают расчёт. Отчёт показывает количество повышений и предупреждает, что расчёт основан на текущих данных. Сервер повторно проверяет все значения; UI не заменяет серверную валидацию.

В разделе «Уровни» администратору доступна ссылка «Изменить уровни». Менеджеру и наблюдателю редактирование не показывается. Юридические документы выделяются заголовком и якорной ссылкой, с отдельными состояниями загрузки, ошибки и успешной публикации.

Приёмка: длинный текст привилегии читается на desktop; после проверки ввод причины и отметка подтверждения оставляют публикацию доступной; новый порог снова требует проверки. Публикация не меняет старые аренды.

## 4. Защита введённых данных — UX-03

Модальные формы после изменения поля предупреждают перед закрытием через Escape, крестик или фон. Предложить «Продолжить редактирование» и «Закрыть без сохранения». Пустые неизменённые формы закрываются сразу. Успешное сохранение закрывает форму без лишнего предупреждения; ошибка сохранения оставляет данные в форме. Во время запроса нельзя закрывать форму или повторно отправлять её.

Для длинных самостоятельных форм предусмотреть защиту при уходе со страницы и обновлении вкладки. Предупреждение не является автосохранением: это явно не обещать. Не допускать применения общей защиты к навигационному меню и просмотровым окнам.

Приёмка: в форме нового автомобиля ввести название, нажать Escape, продолжить редактирование — название сохранено; закрыть без сохранения — окно закрыто. Ошибка API не уничтожает введённое.

## 5. Ручные аренды — UX-04

Заменить выбор из первых 50 клиентов поиском по имени, телефону или ID участника через существующий API. В результатах показывать имя и телефон/ID; различать загрузку, пустой результат и ошибку. Сохранять выбранного клиента при изменении поискового запроса; устаревший ответ не должен подменять новый.

Внешний ID подписать как идентификатор из системы учёта и объяснить назначение: защита от дублирования. Не менять контракт интеграции и не генерировать дубли незаметно. Название автомобиля разрешено вводить вручную; если есть автопарк — предложить выбор с возможностью ручного ввода.

В окне изменения статуса показать клиента, автомобиль, даты, сумму и текущий статус оплаты. Основная кнопка «Сохранить статус», отмена — текстовая «Отмена». Сохранить контроль версии записи и допустимых переходов на сервере.

Приёмка: можно найти клиента за пределами первых 50; нельзя сохранить без выбранного клиента; конфликт версии требует обновления; открытие и закрытие формы не меняет аренду.

## 6. Контент и публикация — UX-05

Для автомобиля, маршрута и статьи добавить загрузку изображения через существующий сервис медиа; ссылку оставить дополнительным способом. Общая реализация с редактором предложений: допустимые форматы/размеры, индикатор загрузки, предпросмотр, ошибка, замена. Сервер проверяет фактическое содержимое файла; произвольный путь к файлу не принимать.

Около публикации предложения/маршрута объяснять, что при включённом соответствующем автоматическом уведомлении публикация может отправить сообщение участникам. Показывать условия и аудиторию по действующим правилам; не обещать точное количество адресатов без расчёта. Сохранение черновика не должно создавать событие публикации. Не менять настройки рассылок автоматически.

Приёмка: фото можно выбрать без внешнего фотохостинга; невалидный файл показывает понятную ошибку; повтор сохранения не создаёт повторную рассылку; сообщения в тестах направлены только в тестовый транспорт.

## 7. Приглашения и ручные награды — REF-01…REF-08

### 7.1 Настройка

В «Приглашениях друзей» две зоны: «Условия программы» и «Приглашения и награды». Администратор редактирует включение программы, название награды и условия для каждой стороны. Обязательные ограничения: название 1–120 символов, условия 1–2000 символов, причина изменения 3–1000 символов. Перед публикацией показывается текст для обеих сторон. Пока условия не заполнены, включение невозможно.

Условия сохраняются отдельными неизменяемыми версиями с автором, временем публикации и причиной. Отключение прекращает создание новых обязательств, но не удаляет ранее возникшие. Новая версия не переписывает уже созданные награды.

### 7.2 Переход без изменения старых аренд

При первой активации ручной программы зафиксировать границу времени. Награды по новой схеме создаются только по новым операционным арендам, созданным после этой границы. Импорт истории и уже существовавшие на момент активации аренды не инициируют новые награды. У существовавших аренд сохраняется прежняя логика и снимки; никаких ретроспективных начислений или массовых перепривязок.

До активации ручной программы действует прежний контракт. На экране явно различать старые Bonus и новые ручные награды. Скрытие старых полей не должно незаметно менять действующие числовые настройки. Условия перехода реализовать тестами до включения новой схемы.

### 7.3 Создание наград

Сохранить существующую проверку валидности приглашения: один пригласивший, запрет самоприглашения, ограничения заблокированных участников и первой подходящей аренды. Создание — в той же транзакции, что квалификация аренды, либо через устойчивое идемпотентное задание, без потери события при сбое.

Для каждой стороны создать отдельную запись: приглашение, получатель, роль стороны, аренда-основание, версия условий, снимок названия и условий, статус, время создания. Уникальность по приглашению и стороне исключает повторы. Новая награда не начисляет Bonus и не уменьшает сумму аренды.

### 7.4 Выдача и отмена

Статусы: «Ожидает выдачи», «Выдана», «Отменена», «Требует проверки». Менеджер/администратор открывает карточку с получателем и основанием, нажимает «Отметить выдачу», подтверждает фактическую выдачу и вводит комментарий. Хранить автора, время, комментарий. Повторный запрос идемпотентен; конкурентная выдача не создаёт вторую запись.

При отмене аренды до выдачи награда отменяется. Если награда уже выдана, сохранить факт выдачи и отметить необходимость проверки; не списывать деньги или Bonus и не объявлять подарок автоматически возвращённым. Все переходы пишутся в журнал. Наблюдатель имеет только чтение.

### 7.5 Отображение

В таблице: оба участника, статус приглашения, награда каждой стороны, статус выдачи, аренда-основание. Фильтры по статусу и поиск по участнику; пагинация. В клиентской части показывать действующие условия приглашения и собственные возникшие награды; не показывать чужие персональные данные. Не обещать Bonus при ручной программе.

### 7.6 Проверка

Интеграционные сценарии: первая оплаченная завершённая аренда; неоплаченная/незавершённая; исторический импорт; старая аренда; повтор события; смена версии до/после квалификации; отключение программы; блокировка и повтор; два параллельных подтверждения выдачи; отмена до/после выдачи; роли; запрет выдачи чужой/несуществующей награды. Проверить, что миграция не обновляет таблицу rentals и существующие финансовые записи.

## 8. Журнал и доставка — OPS-01

Показывать имя сотрудника и понятное описание действия; технический код и ID доступны в деталях. Системные действия обозначать как «Система». Для неизвестного кода сохранять исходное значение, не скрывать событие.

В доставках показывать получателя, тип события, время, переведённый статус, попытки и понятную причину. suppressed — «Не отправлено по правилам». Технические подробности доступны отдельно администратору, без токенов и секретов. Кнопка повтора не должна обходить отписку и ограничения получателя.

## 9. Диагностика фоновых задач — OPS-02

На проверенном сервере обнаружены два job_maintenance с общим текстом, без причины. Причина пока не установлена; существующий текст недостаточен для объявления исправления.

Добавить в диагностику этап выполнения, безопасный код ошибки и идентификатор запуска. Не сохранять секреты, полный DSN или произвольный stack в пользовательском интерфейсе. Различать успешный запуск обработчика и успешное обслуживание. Ошибку этапа закрывать только после успешного соответствующего этапа; частичный успех не маскирует сбой. Повторное задание не должно дублировать начисления/уведомления.

Приёмка: искусственный сбой этапа на локальных данных виден с названием этапа; следующий успешный проход отражён отдельно; исходные live-ошибки не удаляются в ходе разработки.

## 10. Материалы от заказчика

Нужен утверждённый логотип (предпочтительно SVG, также PNG с прозрачным фоном), при наличии — правила использования. Названия/условия наград заказчик заполнит в админке. Точные новые проценты, пороги и юридические тексты не придумывать и не публиковать от имени заказчика. Фото и тексты контента можно добавлять через улучшенные формы.

## 11. Порядок реализации и критерий готовности

1. Интерфейс без финансовой миграции: UX-01, UX-02, UX-03.
2. Операционные формы и контент: UX-04, UX-05, OPS-01.
3. Версии ручных наград, миграция, API, интерфейс и интеграционные тесты: REF-01…08.
4. Диагностика OPS-02 и общий регресс.

Для каждого этапа: typecheck, lint, релевантные тесты; для UI — реальные проверки desktop/mobile. Полный прогон интеграции требует отдельной локальной тестовой PostgreSQL, не действующей базы. Пропущенные проверки указывать явно. Финальная готовность: все перечисленные сценарии пройдены, изменения рассмотрены по diff, нет неожиданных изменений старых аренд, подготовлены шаги выкладки/отката. Наличие спецификации и первого этапа не означает готовность всей системы.

## 12. Реализация и проверка — 22 сентября

Реализованы все четыре пакета из раздела 11: навигация и настройки, защита самостоятельных и модальных форм, поиск по всей базе клиентов, контекст аренды, загрузка фото с предпросмотром, предупреждения о публикациях, понятные журналы, ручная реферальная программа и диагностика фоновых задач. Условия наград задаёт администратор, фактическую выдачу подтверждает менеджер. Старые аренды массово не изменяются.

Миграция проверена на двух отдельных локальных PostgreSQL-базах. Полный автоматический прогон: 155 тестов в 25 файлах прошли, без пропусков. Проверены конкурентная выдача и отмена, повторные запросы, версии условий, блокировка, выключение программы, старые и исторические аренды, роли и приватность клиентского ответа.

Проверено в браузере с настоящими API и локальной БД: публикация условий; поиск клиента за пределами первых 50; создание оплаченной завершённой аренды; появление двух наград; выдача администратором и менеджером; режим чтения наблюдателя; загрузка и сохранение фотографии автомобиля; контекст аренды; оба варианта предупреждения о несохранённых изменениях. На ширине 390 px меню читается, горизонтального переполнения страницы нет. В проверенной вкладке ошибок/предупреждений консоли нет. Ранее отдельно проверены сохранность модального ввода, возврат фокуса и расчёт порогов на desktop/mobile.

Проверка закрытия вкладки нативным beforeunload-диалогом не автоматизирована. Две прежние live-ошибки обслуживания не объявляются исправленными: добавлена диагностика для установления причины следующих сбоев. Облачная миграция, выкладка и включение программы в рабочей базе не выполнялись. Порядок выпуска и ограничения отката — в ADMIN-UX-RELEASE.md. Для запуска нужны утверждённый логотип и реальные условия от заказчика.
`npm run typecheck`, `npm run lint` и `npm run build` прошли. Повреждённый временный файл типов dev-сервера был удалён после его остановки; исходный код для обхода проверки типов не менялся.
