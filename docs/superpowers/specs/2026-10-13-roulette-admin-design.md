# Рулетка призов: настройки, попытки и контроль розыгрышей

## Цель и границы

Администратор должен понимать состояние рулетки и управлять ею без знания внутренних полей базы данных. Шансы задаются в настройках рулетки, а карточка приза содержит только описание, награду и ограничения её применения. Каждый успешный прокрут выдаёт приз. Попытки выдаются только тремя способами: один раз за завершённую регистрацию, по промокоду и вручную. Ежедневных попыток и начисления за аренды в новой модели нет.

Выпуск не включает включение розыгрыша в production: существующий серверный флаг `ROULETTE_ECONOMICS_APPROVED` остаётся обязательным. Экономические правила призов утверждаются отдельно до включения.

## Интерфейс администратора

Раздел `/admin/roulette` содержит пять понятных блоков.

1. **Состояние.** Явный статус «Открыта/Выключена», причины невозможности запуска, срок действия награды, переключатель запуска и подтверждение экономических правил. Показывать отдельно состояние серверного допуска.
2. **Шансы.** Одна таблица всех призов, включённых в розыгрыш. Для каждого задаётся доля в процентах; сумма настроенных долей равна 100%. Рядом показываются фактические шансы для выбранного уровня участника с учётом минимального уровня, дат и исчерпанного лимита выдач. При изменении доступного пула оставшиеся доли нормализуются. Если для какого-либо уровня нет доступных призов, интерфейс предупреждает и открытие рулетки блокируется; если пул опустел позднее, прокрут для этого участника недоступен без расходования попытки. Сохранение атомарно меняет веса и версию настроек с записью автора в журнале. Редактор карточки приза поля шанса не содержит.
3. **Попытки.** Регистрация: включить/выключить и задать число попыток за первый переход участника в активный статус. Начисление происходит один раз на участника и только для регистраций после включения правила. Ручная выдача: поиск участника, число попыток от 1 до 100, обязательная причина и подтверждение. Общий срок действия начисленной попытки настраивается, исходное значение — 30 дней; срок отсчитывается от начисления, в том числе после применения промокода.
4. **Промокоды.** Администратор создаёт случайный код, каждый успешный ввод которого даёт ровно одну попытку. У кода есть период действия, общий лимит применений и переключатель активности. Один участник может применить конкретный код один раз. Код нормализуется без пробелов и без учёта регистра, создаётся из криптографически случайных данных с не менее чем 128 битами энтропии. Полный код показывается для копирования при создании; в списке отображаются статус и число применений. Участник вводит код на экране рулетки и сразу видит результат.
5. **Призы и проверка.** Список призов показывает статус, награду, срок и лимит. Форма сначала показывает основные поля, редкие условия раскрываются отдельно, рядом доступен предпросмотр. Проверка показывает историю начислений и прокрутов с поиском по участнику, дате и призу, а также заданные и наблюдаемые распределения с размером выборки. Числа в статистике не выдаются за доказательство честности случайного выбора.

Роль `viewer` только читает. Настройки шансов, правила попыток, промокоды и ручную выдачу меняет `admin`; редактирование описания призов сохраняет существующую роль `manager`. Все ошибки показываются рядом с действием, не стирая введённые данные.

## Модель данных и начисления

Существующие `roulette_prizes`, `roulette_settings`, `roulette_spins` и `roulette_awards` сохраняются. Новая миграция добавляет настройки регистрационного начисления и срока попыток, таблицу источников попыток и таблицы промокодов и их погашений. Источник попытки содержит участника, тип (`registration`, `promo`, `manual`), уникальный ключ события, число выданных и использованных попыток, срок действия и автора/причину. Уникальность `(user_id, source_type, source_key)` исключает повторное начисление.

Факт завершения регистрации — первый переход `users.status` в `active`. Он фиксируется в БД отдельным неизменяемым временем первой активации; существующим активным участникам время заполняется при миграции как историческое. Идемпотентная фоновая сверка создаёт попытки для новых активаций после времени включения правила и переживает сбои воркера. При включении правила существующие активные участники попыток задним числом не получают. Изменение количества попыток влияет только на новые активации. Повторная активация того же участника не начисляет попытки вновь.

Промокод хранится в виде хеша; повтор одного кода одним участником и превышение общего лимита отвергаются в транзакции. Создание кода и ручное начисление требуют авторизации администратора, защиты от повтора запроса и аудита. Ручное начисление не может быть выполнено без причины.

Старые розыгрыши и награды остаются читаемыми: старый внешний ключ на дневное начисление сохраняется для старых прокрутов, новые прокруты ссылаются на новый источник. Неизрасходованные ежедневные попытки, уже зафиксированные до перехода на новую модель, действуют до конца своего московского дня и затем истекают; новые ежедневные попытки не создаются. Миграция и код не удаляют историю.

## Прокрут и честность

Сервер, а не браузер, выбирает приз. В одной транзакции он блокирует счёт участника, проверяет действующую попытку и доступный пул, выбирает приз через `crypto.randomInt` по целочисленным весам, расходует одну попытку, создаёт запись прокрута и награду. Повтор запроса с тем же ключом возвращает исходный результат. При ошибке транзакция не расходует попытку и не выдаёт награду.

Для каждого прокрута сохраняются версия настроек, источник попытки, список доступных призов с весами, диапазон случайного выбора и выпавший номер. Это позволяет пересчитать результат и проверить, что выданный приз соответствовал действовавшим шансам; запись сама по себе не доказывает случайность генератора. Изменения шансов и призов остаются в аудите с автором и временем. Ожидаемое число выдач в статистике считается по снимкам шансов каждого прокрута, а не по текущим настройкам. В интерфейсе проверки показываются отказы из-за отсутствия попытки, повторного промокода и недоступного пула. Полные персональные данные и секреты промокодов в журнал не попадают.

Шансы в процентах являются настроенной базовой долей. Фактическая доля меняется, когда приз недоступен по уровню, сроку или лимиту. Участнику не обещается постоянный процент; администратор видит расчёт для каждого уровня до сохранения и после него.

## Ошибки и проверка

- Нельзя открыть рулетку без серверного допуска, утверждения экономических правил и хотя бы одного доступного приза для каждого уровня.
- Нельзя сохранить таблицу шансов с отрицательными значениями, суммой не 100% или устаревшей версией настроек.
- Истёкший, выключенный, исчерпанный или уже применённый промокод не начисляет попытку; ответ объясняет причину без утечки секретов.
- Истёкшая попытка не расходуется. При нескольких источниках сначала расходуется попытка с ближайшим сроком окончания.
- Проверяются конкурентные прокруты, повторный запрос, повторная активация, параллельное применение промокода, смена шансов во время прокрута и отказ посередине транзакции.
- Проверяется отображение шансов для разных уровней, скрытие поля шанса из карточки приза и понятность пустых состояний в админке и у участника.

## Порядок внедрения

Сначала миграция и серверная логика начислений/розыгрыша с тестами, затем API и интерфейс администратора, затем ввод промокода и список попыток у участника. Перед переключением проводится резервное копирование и проверка миграции. В production рулетка остаётся выключенной до отдельного утверждения экономических правил и серверного допуска.
