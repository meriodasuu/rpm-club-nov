## 1. [P1] Один CRM ID может получить два профиля при конкурентном импорте

**Место:** `src/lib/imports/service.ts:10–16`, `resolveCustomer`. Категория: идентичность/целостность экономики.

**Сценарий:** два параллельных API/import запроса содержат одинаковые source=rpm и CRM ID, но разные новые телефоны. Каждый получает собственную phone-блокировку, SELECT обоих не находит клиента. Оба создают разные users с одинаковым `crm_customer_id`: поле не UNIQUE. Если оба SELECT внешней идентичности выполняются до INSERT конкурента, оба считают связь свободной. INSERT проигравшего ждёт конкурента и выполняет ON CONFLICT DO NOTHING, после чего функция без повторной проверки возвращает его собственный второй userId.

**Последствие:** оба запроса могут провести аренды по одному CRM-клиенту на разные Bonus-счета, хотя внешняя идентичность указывает только на один из них. Конфликт телефона должен блокировать присвоение экономической истории, но скрывается ON CONFLICT. Последующие обращения могут получить IDENTITY_CONFLICT уже из-за созданного раздвоения.

**Исправление:** сериализовать также `(source, crmCustomerId)` и после конфликтующего INSERT проверять фактического владельца внешней идентичности до возврата userId; проигравшую транзакцию откатывать. Порядок identity/phone-блокировок должен быть стабильным.

**Регрессия:** два соединения и барьер перед регистрацией identity; одинаковый CRM ID, разные телефоны. Успешен только один запрос; второго профиля/его аренды не возникает. Требования: §6.1, §8 — однозначная идентичность и отказ при конфликте.

## 2. [P1] Сортировка смешанного импорта изменяет начисленный cashback

**Место:** `src/lib/imports/service.ts:51`. Категория: экономическая корректность.

**Сценарий:** operational-файл содержит две аренды одного нового клиента: 95 000 ₽ с endDate=2026-09-01 без qualifiedAt и 10 000 ₽ с endDate=2026-09-02 и явным qualifiedAt. Обе даты в прошлом, ставки стандартные. ORDER BY `qualifiedAt NULLS LAST` обрабатывает позднюю аренду раньше ранней, потому что последняя не содержит timestamp.

**Последствие:** фактически начисляется 200 + 2 850 = **3 050 Bonus**. При предусмотренном §5.3 порядке квалификации должно быть 1 900 + 300 = **2 200 Bonus**. Это не косметический порядок истории: ставка сохраняется на момент каждой обработки, переплата 850 остаётся в ledger.

**Исправление:** определить нормализованный эффективный qualifiedAt для каждой строки до сортировки, включая документированный fallback конца московского дня; сортировать именно этот timestamp, затем externalRentalId. Использовать то же значение при проведении, включая переходы между чанками.

**Регрессия:** указанный смешанный файл, а также файл более 100 строк; порядок и итог должны совпадать с сортировкой по реальному моменту квалификации. Требования: §5.2–5.3, §8.2.

## 3. [P1] Повышение сотрудника до admin сохраняет доступ без MFA

**Место:** `src/lib/api/admin.ts:85`; потребитель `src/lib/auth/session.ts:36–39`. Категория: аутентификация/RBAC.

**Сценарий:** manager входит паролем и получает rpm_staff. Действующий admin повышает его через POST admin/team. Команда меняет membership, но не отзывает старую сессию и не фиксирует уровень подтверждения MFA. Уже на следующем запросе requireStaff получает новую роль admin и разрешает настройки экономики, аудит и управление командой с прежним cookie, хотя MFA для этой сессии никогда не выполнялась. Даже отсутствие настроенного TOTP не мешает такому доступу; проверка MFA присутствует лишь в новом login.

**Исправление:** проверять подтверждение MFA сессии при предоставлении admin-прав. Минимальный вариант с отзывом сессий при повышении должен также исключать гонку с незавершённым login; явный assurance/MFA-признак на сессии надёжнее связывает проверку с каждым запросом.

**Регрессия:** manager login → promotion → admin/settings со старым cookie запрещён до MFA; обычное изменение/отзыв роли продолжает действовать на следующем запросе. Требование: §14 — MFA для admin.

## 4. [P2] Повторная активация из второй сессии не привязывает её к клиенту

**Место:** `src/lib/auth/routes.ts:41`, пропущенное действие на строке 53. Категория: активация/сессии.

**Сценарий:** новый Telegram-клиент получает две сессии до вступления, обе с user_id=NULL. Первая завершает активацию. Вторая вызывает me/activate: текущий пользователь уже active, поэтому early return отдаёт activated=true, не заполняя miniapp_sessions.user_id второй сессии.

**Последствие:** следующий GET me с этой сессией возвращает ONBOARDING_REQUIRED; повторное activate снова сообщает успех и ничего не исправляет. Пользователь вынужден повторно авторизоваться, несмотря на успешный ответ API.

**Исправление:** в идемпотентной ветке привязать текущую сессию к найденному пользователю внутри той же транзакции, сохраняя проверки отзыва и блокировки.

**Регрессия:** две сессии одного Telegram ID до активации; после последовательной либо конкурентной активации обе читают один и тот же свой профиль. Требования: повтор входа и безопасная повторная отправка активации.

## 5. [P2] Кампания может отправить редакцию Drop, которую сотрудник не подтверждал

**Место:** `src/lib/api/operations.ts:52–62`; `src/lib/jobs/telegram.ts:19–22`. Категория: конкурентные изменения/контракт доставки.

**Сценарий:** POST campaigns читает offer v1 и аудиторию. Параллельное PATCH сохраняет v2, например меняет цену/описание. POST затем проверяет expectedVersion=1 против своей устаревшей копии и создаёт кампанию v1. SELECT/version-check не находятся под блокировкой внутри транзакции кампании. В outbox записан только offer_id, а consumer читает актуальное содержимое offers — поэтому реально отправляется v2. Аналогично уже стоящая в очереди кампания незаметно меняет текст при последующем редактировании предложения.

**Последствие:** защита expectedVersion обходится гонкой; публикация новой редакции фактически запускает её отправку через ранее подтверждённую кампанию. Уникальность `(offer_id,offer_version)` не предотвращает отправку неправильного содержимого и последующий повтор v2 отдельной кампанией. Consumer повторно проверяет согласие, active и tier, поэтому утечка предложения неподходящему tier здесь не заявляется.

**Исправление:** проверять версию и создавать кампанию под общей блокировкой offer. Связать доставку с подтверждённой редакцией: сохранять snapshot текста/условий либо подавлять устаревшую версию с явным новым подтверждением. Текущие проверки доступности/согласия сохранить.

**Регрессия:** барьер между чтением offer и созданием кампании, затем PATCH; устаревший POST получает 409. Редактирование после постановки в очередь не отправляет новую редакцию по старому подтверждению. Требования: §11 — публикация и массовая отправка разные действия; version/audience snapshot.

## 6. [P2] Preview не проверяет существующие аренды и конфликт идентичности

**Место:** `src/lib/imports/service.ts:24–25`. Категория: валидация импорта/соответствие приёмке.

**Сценарий:** загрузить файл с внешним ID уже проведённой аренды, но другой суммой, и со строкой, где CRM ID и телефон принадлежат разным существующим клиентам. Preview выполняет лишь синтаксическую нормализацию и поиск дублей внутри файла; ни rentals, ни users, ни customer_external_identities не читаются. Обе строки возвращаются valid без ошибок. Неоплаченные записи также не выделяются как не дающие экономического эффекта.

**Последствие:** сотрудник подтверждает «проверенные строки», а известные до запуска конфликты обнаруживаются только при commit; результат preview не позволяет проверить обещанный состав переноса. Это не повторная проверка commit, которая нужна при изменениях между этапами: первая предметная проверка здесь отсутствует полностью.

**Исправление:** добавить read-only классификацию new/duplicate/conflict/nonqualifying/errors с теми же правилами идентичности и сравнения payload, что применяются при проведении. Повторную проверку при commit оставить; preview не должен создавать клиентов.

**Регрессия:** файл со всеми пятью категориями; до commit видны соответствующие результаты, клиентские/экономические таблицы не изменились. Требование: §8.2, шаги 2–4.
