## Закрытие CORE-REVIEW

| Исходное замечание | Статус | Основание по финальному коду |
|---|---|---|
| Квалификация скорректированной unpaid-аренды использовала исходную сумму | Закрыто | `processRental` берёт `old.current_amount_kopecks` для total и cashback; корректировка/отмена продолжают использовать эту же текущую сумму. |
| Integration не мог выполнить adjust/cancel | Закрыто | Allowlist разрешает три rental-команды; источник проверяется в core для новой и существующей аренды/коррекции. Integration source включён в idempotency hash. Ручные Bonus и настройки не разрешены. |
| Сегодняшняя completed/paid аренда без qualifiedAt отклонялась | Закрыто | `resolveQualifiedAt` использует момент подтверждения для сегодняшней operational-аренды. Исторический fallback остаётся концом московского дня. Неявный timestamp стабильно представлен в payload hash, повтор не становится конфликтом только из-за времени запроса. |
| Ожидание account lock позволяло потратить истёкший lot | Закрыто | После блокировки счёта обновляется время через `clock_timestamp()`. Перед списанием оно обновляется ещё раз; expiry и consume используют один cutoff. Обычный spend дополнительно отвергает непокрытый остаток вместо создания debt. |

Дополнительно проверен ограниченный пересчёт tiers: `recalculateTiers` принимает limit/cursor/version, обрабатывает максимум 100 счетов, задаёт lock_timeout и возвращает следующий cursor. Обработчик PROGRAM_PUBLISHED сохраняет cursor и помечает событие завершённым только после последней страницы. Повтор после сбоя не создаёт повторного повышения, если состояние уже обновлено.

| Preview не выявлял предметные конфликты | Закрыто по исходным сценариям | Preview читает существующие rentals/users, сравнивает идентичность и содержимое, отмечает duplicate и конфликтные invalid-строки, добавляет classification=nonqualifying. Во время preview записываются только служебные batch/rows/audit. |

## Новый MFA enrollment

Прочитан добавленный поток `auth/staff/login`. Настройка TOTP возвращает enrollment без выдачи staff-cookie. Существующий verified TOTP имеет приоритет над переданным factorId; unverified factor выбирается только из списка факторов вошедшего Supabase-пользователя. Выдача сессии проходит после успешного challengeAndVerify и повторной проверки membership под блокировкой. Нового подтверждённого обхода MFA в этом потоке не выявлено.
