# RPM Club: параметры интеграции с БД

## 1. Подтверждённая конфигурация

- СУБД: PostgreSQL 17.
- Production database: `rpm_club`.
- Основная схема: `public`. Схема `extensions` используется для расширений PostgreSQL; прикладные таблицы находятся в `public`.
- Production PostgreSQL работает во внутренней Docker-сети. Порт 5432 наружу не опубликован.
- Тестовая БД: `rpm_club_test`, локальный адрес разработчика `127.0.0.1:55432`. Это адрес тестового окружения, не production endpoint; доступность сервиса зависит от запущенного локального PostgreSQL.
- PostgreSQL доступен сервисам того же VPS через внутреннюю Docker-сеть `rpm-club_backend`, имя `rpm-club-db`, порт `5432`.
- Подготовлены в production read-only представление `integration.v_members` и группа прав `rpm_club_integration_ro`. Группа не имеет LOGIN; парольный пользователь для нового проекта ещё не создан.

## 2. Предлагаемая область read-only доступа

Не выдавать интеграции SELECT на все таблицы `public`. Создать отдельную схему `integration` с представлениями и отдельную роль, имеющую только `CONNECT` и `SELECT` на утверждённых представлениях. Не выдавать права на базовые таблицы, sequence, функции записи, миграции или администрирование.

Предлагаемое представление `integration.v_members`:

| Поле | Назначение |
|---|---|
| `user_id` | Канонический UUID RPM Club; ключ для связи, не отображать клиенту без необходимости |
| `public_member_id` | Публичный ID участника для отображения и поиска |
| `name` | Отображаемое имя |
| `status` | Статус учётной записи: `pending`, `active`, `blocked` |
| `member_since` | Дата вступления в программу, если заполнена |
| `achieved_tier` | Текущий достигнутый уровень программы |
| `total_rental_amount` | Накопленная сумма квалифицируемых аренд; хранится в копейках |
| `created_at` | Дата создания учётной записи |

Телефон, Telegram ID/username, согласия, бонусные остатки и история операций не включены в базовый набор: это персональные или финансовые данные. Добавлять их в отдельное представление следует только при подтверждённой необходимости и явном перечне полей.

Фактические исходные таблицы: `public.users`, `public.loyalty_accounts`. Интеграции следует читать только представление, а не эти таблицы напрямую. SQL настройки хранится в [rpm-club-integration-readonly.sql](../deploy/rpm-club-integration-readonly.sql).

## 3. Устойчивый ID связи

- Основной ключ RPM Club: `users.id` (UUID). Это канонический неизменяемый ID для ссылок между системами.
- Отображаемый идентификатор: `users.public_member_id` (уникальная строка участника). Подходит для интерфейса и ручного поиска; не использовать вместо UUID как технический foreign key.
- Для ID клиента во внешней системе использовать таблицу сопоставления `customer_external_identities`: пара `(source, crm_customer_id)` однозначно связана с `user_id`. Значение `source` необходимо согласовать для каждой интеграции.
- Не связывать записи только по телефону, Telegram ID или username: значения могут отсутствовать или меняться.
- Для аренды предусмотрен уникальный `rentals.external_rental_id`; запись также ссылается на участника через `rentals.user_id`.

## 4. Подключение к серверу

Операторский SSH доступ (это доступ к серверу, не read-only доступ к БД):

```powershell
ssh -i "C:\Users\wthtw\.ssh\rpm_club_deploy_20261006_v2_ed25519" -p 2222 deploy@91.222.239.130
```

Приватный ключ находится по указанному пути; его содержимое и пароль ключа не включать в документы, переписку или команды. Для нового проекта на этом же VPS подключите только его контейнер к приватной Docker-сети RPM Club; порт 5432 наружу не открывается.

Пример фрагмента `docker-compose.yml` нового проекта:

```yaml
services:
  new-project:
    networks:
      - default
      - rpm-club-db

networks:
  rpm-club-db:
    external: true
    name: rpm-club_backend
```

Параметры подключения из контейнера: host `rpm-club-db`, port `5432`, database `rpm_club`, schema `integration`, view `v_members`. Парольный LOGIN-пользователь будет отдельным для нового проекта и включён в группу `rpm_club_integration_ro`; его пароль следует передавать только через secret/env-файл с ограниченными правами.

## 5. Что требуется для выдачи доступа

Чтобы создать отдельный LOGIN-пользователь и подготовить секрет для сервиса, нужно зафиксировать:

1. Название и владелец системы-потребителя.
2. Название Docker Compose-сервиса или каталога нового проекта на VPS.
3. Нужные дополнительные поля из раздела 2 и цель обработки персональных данных, если они нужны.
4. Окружения и срок доступа (test/production).

Пока настроены данные и read-only права; парольный логин ещё не выдавался.
