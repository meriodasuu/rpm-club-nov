# Админка RPM Club: выпуск изменений от 22 сентября 2026

## Что меняется

Меню, настройки программы, защита форм, поиск клиентов, загрузка изображений, контекст аренд, журнал действий и доставка сообщений. Ручные награды за приглашения выделены в отдельный раздел: заказчик публикует условия для двух сторон, менеджер подтверждает фактическую выдачу. Клиент видит действующие условия и только свои награды.

## Данные и совместимость

Новая миграция добавляет `referral_program_versions`, `referral_manual_awards` и ссылку `referrals.manual_version_id`. Она не обновляет аренды или бонусные проводки. RLS включён, прямые права anon/authenticated отозваны, доступ идёт через сервер с проверкой роли. Условия и факт выдачи защищены триггерами от перезаписи.

До первой активации ручной программы действует прежняя механика. После активации ручная программа применяется только к новым операционным арендам, созданным после границы активации. Условия фиксируются при квалификации первой завершённой оплаченной аренды. Для старых аренд сохраняется прежний путь, без массовых пересчётов. Исторический импорт не создаёт ручные награды. Приостановленная программа не создаёт новые награды; уже возникшие остаются.

Отмена аренды переводит невыданную награду в «Отменена». Выданная остаётся с автором и временем выдачи и получает статус «Требует проверки». Автоматического возврата подарка, денежного списания или скидки нет.

## Порядок выкладки

1. Убедиться, что выбран правильный проект и есть актуальная резервная копия базы. Проверить новую миграцию на отдельной тестовой базе.
2. Применить только новую миграцию до переключения приложения. Старые SQL-файлы не изменять и не переигрывать. Обычный push кода сам по себе эту миграцию не применяет.
3. Выложить приложение и проверить вход admin/manager/viewer, чтение уровней, настроек, приглашений и истории. Миграция сама не включает ручную программу.
4. Проверить загрузку фото в настроенный bucket. Локальное файловое хранилище предназначено только для разработки; в production нужен существующий Supabase Storage.
5. Заказчик заполняет и проверяет названия/условия обеих наград, затем включает программу в админке. Не публиковать тестовые условия в рабочей базе.
6. Проверить первый реальный цикл по согласованному тестовому сценарию: первая оплаченная аренда → две ожидающие награды → отметка выдачи → журнал. Массовые рассылки для проверки не запускать.

## Откат

До активации ручной программы можно вернуть предыдущую версию приложения, оставив добавленные таблицы: старый код ими не пользуется. Не удалять новые таблицы и историю.

После активации откат только к старому коду небезопасен: он не обрабатывает ручные награды при отмене аренды. Предпочтителен исправляющий выпуск. При необходимости остановки отключить создание новых наград через новую редакцию, сохранить поддержку уже возникших наград и согласовать обслуживание незавершённых операций. Не переписывать старые аренды ради отката.

## Ограничения диагностики

Новые ошибки фонового обслуживания содержат этап и безопасный код. Два ранее найденных live-сбоя не имели этих данных: добавленная диагностика не доказывает устранение их исходной причины. Проверить следующие запуски после выкладки; старые ошибки без этапа автоматически не закрываются.

## Материалы для запуска

Утверждённый логотип, реальные названия и условия наград, готовые юридические тексты и заполненный контент. Новые проценты и пороги программы не публиковались в ходе разработки.
