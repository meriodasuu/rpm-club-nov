# Запуск RPM Club на VPS

Для существующего сервера RPM Rent применяется [схема Docker + Caddy](VPS-RELEASE.md). Описанные ниже systemd/nginx — альтернативные шаблоны для отдельного сервера.

Шаблоны рассчитаны на Debian/Ubuntu с systemd, Node.js 22 и nginx. До применения проверить ОС, путь Node (`command -v node`), свободные ресурсы, существующие сайты и службы. Команды здесь являются инструкцией для следующего этапа; конфигурация на сервере ещё не применена.

## Ресурсы и база

2 vCPU / 2 ГБ RAM / 40 ГБ NVMe — исходная конфигурация для одного процесса Next.js и небольшого worker при сохранении внешних Supabase PostgreSQL/Auth/Storage. Это не результат нагрузочного теста конкретного сервера. Полный self-hosted Supabase на этот VPS не переносить в рамках данной схемы. До запуска проверить доступ VPS к Supabase и Telegram. Лимиты двух служб суммарно до 1712 МБ; остаток нужен ОС и nginx, остальные службы учитываются отдельно. `MemoryMax` защищает ОС, но при его достижении процесс будет остановлен.

Сборку и проверки предпочтительно выполнять на отдельной Linux-машине/CI с той же архитектурой и Node 22. Windows node_modules/.next на Linux не копировать: sharp и другие зависимости содержат платформенные бинарники. Если сборка выполняется на VPS, заранее измерить пиковую память; одновременно с рабочим приложением на 2 ГБ её не запускать. Два ядра сами по себе не решают нехватку памяти.

## Адрес

Нужен постоянный HTTPS-адрес. Предлагаемый вариант — `club.rpmrent.ru`, если владелец предоставит управление DNS. Поддомен не требует покупки отдельного домена: создаётся DNS-запись A на IPv4 VPS; AAAA добавляется только при работающем IPv6. Имя ещё не выбрано. Админка использует тот же адрес с `/admin`, отдельный поддомен ей не требуется.

## Подготовка выпуска

1. Создать отдельного системного пользователя `rpm-club` без интерактивного входа. Выпуски хранить в `/opt/rpm-club/releases/<commit>`, `current` — ссылка на выбранный проверенный выпуск. Сохранить прежний выпуск для отката.
2. Выполнить `npm ci`, проверки и `npm run build`. Runtime требует и `tsx` из devDependencies для preflight/worker; в этой схеме не использовать `npm ci --omit=dev`. Не копировать `.env.local`, `.env.vercel`, `.local`, документы с персональными данными или тестовые артефакты.
3. Создать `/etc/rpm-club.env`, права `root:rpm-club 0640`. Взять имена переменных из `.env.example`, значения — из действующего защищённого окружения. `APP_URL` — новый HTTPS origin без пути; `NODE_ENV=production`, `LOCAL_PREVIEW=0`. Сохранить прежний `ENCRYPTION_KEY`: замена сделает MFA-секреты нечитаемыми. Не публиковать env в Git и не печатать его в логах.
4. Сохранить подключение существующей Supabase БД, её CA, Auth и Storage. `DATABASE_URL` runtime должен использовать выделенную ограниченную роль. Миграции применяет администратор БД отдельно. Локальный `docker-compose.yml` использует trust и предназначен только для разработки. Seed на реальной базе запрещён.
5. Проверить форму конфигурации, не вызывая внешних сервисов:

   ```sh
   cd /opt/rpm-club/current
   node --env-file=/etc/rpm-club.env --import tsx scripts/check-production.ts
   ```

   Этот скрипт проверяет только значения окружения. Он не подтверждает доступность БД, действительность ключей, DNS, сертификат или бизнес-настройки.

6. Сверить migration checksums и выполнить резервную копию. При необходимости новых миграций запускать `node --env-file=/path/to/private-migration.env --import tsx scripts/migrate.ts` с административными credentials. Не переигрывать seed/старые миграции. При создании новой БД требуется также настроить runtime-роль и grants: одних миграций недостаточно.

## Службы и HTTPS

1. Скопировать проверенный `rpm-club.service` в `/etc/systemd/system/`. Убедиться, что `.next` существует и доступна для записи пользователю службы; остальной выпуск оставить только для чтения. Проверить путь `/usr/bin/node` и лимиты памяти с учётом других служб.
2. Выдать TLS-сертификат для согласованного имени. Сначала поднять только HTTP-конфигурацию ACME; HTTPS-блок из примера подключать после появления файлов сертификата. Затем `nginx -t`. Настроить автоматическое продление сертификата.
3. Запустить `systemctl daemon-reload`, `systemctl enable --now rpm-club`. Проверить `http://127.0.0.1:3001/api/health` и `/api/ready`, затем те же пути по публичному HTTPS. Порт 3001 не открывать наружу; firewall оставляет согласованные SSH, 80 и 443.
4. Проверить загрузку фотографии и CSV до предельного размера. В nginx задано 12 МБ с запасом для multipart; стандартный предел nginx 1 МБ не подходит.
5. Не создавать новый bot token и не менять encryption key при переносе. После готовности HTTPS переключить webhook, Main Mini App, общее меню и персональное меню владельца на новый адрес, сохранив pending updates. `telegram:setup --check` проверяет общее меню; персональное меню проверяется отдельно. Существующий setup-скрипт намеренно отказывается заменять чужой адрес webhook — перенос выполняется отдельно с проверкой исходного и нового адресов.

## Один планировщик

Выбрать один вариант. Сохранять оба одновременно не нужно.

- Существующий Supabase Cron: поменять только `rpm_club_worker_origin` в Vault после готовности сервера, сохранить `CRON_SECRET`; проверить следующий heartbeat и HTTP 200.
- Локальный systemd timer: сначала отключить прежний cron, затем установить `rpm-club-worker.service` и `.timer`, `systemctl enable --now rpm-club-worker.timer`. systemd не запускает вторую копию уже работающей oneshot-службы. Таймер ждёт минуту после окончания предыдущего запуска. Проверить heartbeat и ошибки.

## Приёмка и эксплуатация

- В Telegram на Android/iPhone: регистрация, контакт, согласия, карта, заявка, подтверждение/выдача/завершение менеджером, прогресс скидки, приглашение и тест уведомления согласованному получателю.
- В браузере: `/admin` через личную ссылку и MFA, роли manager/viewer, фото, импорт, история и выход. Старые сессии другого домена не переносить.
- Нагрузочная проверка на VPS: CPU, RAM, p95, ошибки, пул БД; отдельно проверить загрузку CSV и работу очереди. При росте нагрузки увеличить ресурсы по измерениям.
- Настроить внешние проверки `/api/ready`, возраста heartbeat, ошибок/возраста очереди, свободного диска и срока сертификата. Проверить сохранение журналов и ротацию.
- Ежедневная резервная копия БД и проверка восстановления в изолированной БД без Telegram credentials/worker. Отдельно сохранить конфигурацию и ключи в защищённом хранилище.
- Откат: остановить локальный worker, переключить `current` на совместимый предыдущий выпуск и перезапустить web. Базу со свежими арендами не откатывать старым dump. Если возвращаем Vercel, отдельно вернуть адреса бота/планировщика и проверить их чтением.

Источники: [Next.js self-hosting](https://nextjs.org/docs/app/guides/self-hosting), [Telegram WebAppInfo](https://core.telegram.org/bots/api#webappinfo). Шаблоны systemd/nginx требуют проверки на целевой ОС; Windows-проверки приложения эту часть не заменяют.
